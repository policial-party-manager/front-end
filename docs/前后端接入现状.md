## 必须保留的契约边界

- 支部 `tb_branch`：`branch_name varchar(20)`、`college varchar(10)` 均非空，`secretary_id` 非空且外键指向 `tb_user.id`。`saveBranch` 强制 `status=1` 并调用 `requireSecretaryIsBranchAdmin`；`updateBranch` 不使用传入 `status` 修改状态，且仅在 `secretaryId` 非空时校验书记资格；`deleteBranch` 置 `status=0`。支部状态是 1 正常 / 0 已删除，不是成员表的 1 启用 / 2 停用。
- 前端书记候选链路：`GET /api/v4/admin/roles` 取规范化 `roleCode === "branch_admin"` 的动态角色 ID，再按 `roleId` 调 `GET /api/v4/admin/users/page`；提交的是 `UserVo.id`，不是学号、用户名或角色 ID。角色字典缺少该编码时不得退化为全量成员查询；编辑回显当前书记走 `GET /api/v4/admin/users/{id}`，不受候选分页或搜索影响。
- 支部维护页面以独立会话身份标记隔离退出/换号前的响应，正常 401 令牌刷新保留表单；搜索关键词在请求开始时记录，清空会使在途旧搜索失效；详情与书记查询共享详情请求序号，关闭或切换详情后旧响应不回写。仓库内 `npm run test:branches` 用真实页面及模拟 HTTP 响应验证这些交互，并覆盖保存时刷新和跨标签页身份切换；此类回归不是后端持久化或生产验收。
- `openapi.yaml` 中支部请求体的 `status` 描述（0 未删除 / 1 已删除）与 DDL 及服务实现（1 正常 / 0 已删除）相反，字段语义以服务实现和 DDL 为准，不要盲信过时描述（参见 #43 对模板描述漂移的处理）。
- 后端 `importBranches` 只校验「书记用户id」非空并写入 `secretaryId`，未调用 `requireSecretaryIsBranchAdmin`，与手工新增/编辑路径存在资格校验差异；前端不额外加严，弹窗内写明这条差异。
- 支部模板与导入的前端契约（前端已接，后端只读核对）：模板固定 4 列「支部名称 / 所属学院 / 简介 / 书记用户id」（书记填 `tb_user.id`）；`ImportResult` 与成员导入共用同一 DTO，`{ total, successCount, failCount, errors: [{ row, reason }] }`，`row` 是 Excel 实际行号（表头第 1 行，数据从第 2 行开始）。导入逐行独立处理，单行失败不中断其余行；支部名称必填、书记用户id 非空、名称与任意状态（含软删除）支部重名即失败；导入的支部一律写 `status=1`。响应报错时 `errors[].reason` 原样转达，前端不预判。
- 支部导入不校验书记是否持有 `branch_admin`，但手工新增/编辑校验，因此真实使用中可能出现「导入成功但编辑报错」；这是后端契约不一致，未在本任务修改。跨页同步无需额外机制：`/members` 每次 `onMounted` 都会重新拉取 `/api/v4/admin/branches/options`，导入后新支部天然出现在成员导入与筛选的支部下拉中。
- `#29` 早期评论要求「允许先创建未指定书记的支部」，与当前服务端非空书记 + 支委角色规则冲突。本次按服务端规则实现，是否重新支持空书记需业务决策；不关闭 #29，不修改数据库约束。
- 系统角色是 `super_admin`、`branch_admin`、`student`；政治身份由字典与当前身份字段表达。前端成员类型已接入 `identityId`、`identityName`，只读字典按 records/total 完整分页，不通过字典 roleId 推导登录权限。
- 两套成员分页契约不同：管理员分页保留关键词/支部独立查询及全部状态；新成员分页/导出只支持 identityId、keyword、grade、major、college、status，不支持 branchId/roleId，且 status 默认 1。本次身份模式显式传 1/2，只开放身份与状态，导出使用已应用快照、无分页参数。管理模式禁用导出，显式切换会提示并清理条件。
- 源码确认两类范围缺陷：新 `filterDetailIds` 将用户名命中 ID 直接合并，绕过身份/学院/年级/专业；旧管理员分页的用户名分支也会绕过 branchId。前端分别禁止身份与关键词组合、管理员关键词与支部组合；不客户端过滤或伪造 total。最小反例、接口限制、八项结论见 [Issue #19 验收记录](Issue-19-验收记录.md)。
- 新成员分页仅补 ID，不补支部名/角色/身份名；身份名称可由真实字典补充，其他缺名准确显示，不猜测关联。成员导出列仅为学号、姓名、手机号、邮箱、学院、年级、专业、班级、备注，不包含支部或政治身份列。
- 个人中心 `UserController`（`GET`/`PUT /api/v4/user/profile`，只读核对后端 + 拦截层回归）：
  - `UserProfileVo` 已返回 `identityId`/`identityName`/`contactPerson`/`remark`/`gender`/`identityCardNumber`；本次把前端类型补全后才在页面可见。`identityName` 由身份字典补名、`branchName` 由支部表补名，两者都可能为 null，页面沿用既有口径显示「未登记」「未分配支部」。
  - **部分更新**：`UserServiceImpl.updateProfile` 逐字段 `trimToNull`，为 null 即跳过赋值，因此「未传 = 不改」。前端只提交与打开抽屉时快照不同的字段，不用整表回写。
  - **无法清空（与 `PUT /v4/members/{id}/contact` 同源缺陷）**：空串同样被归一为 null，`userDetailMapper.updateById` 走 MyBatis-Plus 默认 `NOT_NULL` 策略跳过该列，接口返回 200 但库中值不变。因此 `/profile` 不提供清空操作，也不静默忽略：某字段从有值改为空时给出字段级提示并阻止提交，整单不发请求。修复属后端范围（`@TableField(updateStrategy = FieldStrategy.IGNORED)` 或 `LambdaUpdateWrapper.set`）。
  - **前端约束 ≠ 后端约束**：后端物理上仍接受 `realName`/`studentId`/`identityCardNumber`/`gender`/`college`/`grade`/`major`/`className` 的本人更新；本任务只按产品口径在前端锁定为只读，并未在后端禁止，绕过前端直接调用接口依然可改。
  - 校验对齐后端：手机号 `^$|^1\d{10}$`；邮箱正则且 ≤25；紧急联系人 ≤50；备注 ≤500。前端前置校验只为减少无效请求，最终校验在服务端。
- 支委成员 scoped 接口（`MemberController` / `ScopedMemberServiceImpl`，后端只读核对 + 本机真实联调）：`GET /api/v4/members/page`、`GET /api/v4/members/{id}`、`PUT /api/v4/members/{id}/contact`、`GET /api/v4/members/export` 共用 `BranchScopeService` 范围守卫，超管全院、支委限本支部；跨支部与不存在统一返回「用户不存在」。
  - **`branchName` 与 `identityName` 恒为 null**：`buildVos` 只写 `branchId`、`identityId`，不查支部表与身份表。真实联调实测：`branchId` 有值时 `branchName` 仍为 `null`。前端降级为「未分配」/「支部名称不可用（编号 x）」与「未登记」/「身份 #x」，身份名由一次性加载的 `/api/v2/content/identities/page` 字典补齐，不逐行请求。
  - **`status` 缺省即只查启用**：`status != null` 用传入值，否则 `eq(User::getStatus, 1)`。真实联调实测：缺省只返回 `status=1`，显式 `status=2` 只返回停用成员。前端默认不传 `status`，不提供「全部状态」。
  - **「空串清空」实际不生效（真实联调实测，后端缺陷）**：`updateContactScoped` 对入参 `trimToNull`，空串被归一为 `null`，随后 `userDetailMapper.updateById(detail)` 使用 MyBatis-Plus 默认 `NOT_NULL` 更新策略跳过该列，于是接口返回 200 但库中值不变。实测 `phone`/`email`/`remark` 分别 `PUT` 空串后接口回读与库中值均保持原样；对照实验写入另一个非空串则正常，证明是「置 null 被跳过」而非整体失效。前端仍按契约发送空串（唯一能表达清空的取值），修复属后端范围。
  - **缺陷边界（逐层核实，避免误报也避免漏报）**：根因是「`trimToNull` 后写 `null` + MyBatis-Plus 默认 `NOT_NULL` 策略」。因此**只有同时满足两个条件才失效**：（1）该实体的服务在 `updateById` 前把空串归一为 `null`；（2）请求里只提供该字段。
    - **失效**：`tb_user_detail` 的 `phone`/`email`/`remark`（支委 `updateContactScoped` 与**超管** `AdminUserServiceImpl.updateUser → setIfPresent → trimToNull` 都走同一路径，两条入口均实测失效）；同类写法还有 `tb_identity.description`、`tb_activity_leave.reason`、`tb_identity_change.reason`/`review_remark`、`tb_study_record.url`/`remark`、`tb_thought_report.file`/`review_remark`（均为静态核实，未逐一联调）。
    - **正常**：直接传空串、不经 `trimToNull` 的路径，如支部简介 `AdminBranchServiceImpl.updateBranch → setDescription`，实测库中确实变为空串 `""`。同理新闻封面 `setCover`、活动 `setLocationDescription` 均为直接赋值，不受影响。
    - **不受影响**：`UserServiceImpl.updateProfile` 本身就不承诺清空（`trimToNull` 后 `!= null` 才写），故无行为差异；SSO 仅在字段为空时补值，也不依赖清空。
    - **无任何兜底**：全仓 grep 未发现 `UpdateWrapper`/`.set(...)` 显式写 NULL 的路径，因此一旦需要清空就没有绕行手段。
    - **副产品（次要，不影响主流程）**：`updateContactScoped` 的 `after` 快照取的是内存对象而非回读值，`before` 取的是库值，于是在变更日志里会记录一次**实际未发生**的清空；因操作日志是 `@Async` 写 Elasticsearch、失败仅 warn，ES 不可用时该日志本身也不会落盘，所以当前看不到错误痕迹。修复时建议把 `after` 改为 `updateById` 后重新 `selectById` 回读（`AdminUserServiceImpl` 已是回读取快照的正确写法）。
    - **修复要点（后端）**：不要改全局 `update-strategy`（会让所有 `updateById` 把整套字段刷成 null，风险更大）；应为需要清空的字段加 `@TableField(updateStrategy = FieldStrategy.IGNORED)`，或改用 `LambdaUpdateWrapper` 显式 `.set(字段, null)`。
  - 导出列固定为 `EXPORT_HEADERS`：学号、姓名、手机号、邮箱、学院、年级、专业、班级、备注，**不含政治身份与支部列**；真实 xlsx 解析核对一致，行数等于对应条件下服务端 `total` 加表头行。
  - `filterDetailIds` 的 username 命中分支会再查 `tb_user_detail` 并校验本支部，因此支部边界仍成立；被绕过的是 `grade`/`major`/`college`/`identityId` 附加条件（#19 已知缺陷）。前端本页只开放关键词与启用/停用。
  - 支委未归属支部时服务端抛 `IllegalArgumentException`（「您尚未归属任何党支部，请联系管理员」，HTTP 400），前端原样转达；实测页面错误区直接显示该原因。
- 批量启停和调整支部已接真实端点，当前页去重后 1–200，确认、同步防重、会话隔离及结果结构校验，按成员 ID 展示失败，回读失败保留结果，断网/超时不自动重传。正常支部选项不等于后端已验证支部状态；服务实现尚未显式检查目标支部存在和状态。

- 分布统计 `DistributionVo`（`StatisticsController.distribution` 与 `DashboardServiceImpl.distribution` 只读核对）：`dimension` 回显服务端实际采用的维度，`groups[].key` 为维度取值、`total` 为该组全部成员数、`identities[]` 为 `DashboardVo.IdentityCount`（`identityId`/`identityName`/`level` 可能为 null）。
  - `normalizeDimension` 接受 `college`/`major`/`className`/`grade`/`branch` 五个值，`null` 缺省为 `college`，**其他任意值静默回退 `college`**。前端必须比对 `vo.dimension` 与请求维度，不一致时提示实际维度，不得把回退结果标成原维度。控制器 Swagger 注释只写了四个维度、漏了 `branch`，但实现与 `normalizeDimension` 均已支持，以代码为准。

### 政治身份变更（发起与审批）约定

`/development/member/:id` 页头的「发起身份变更」与 `/development/identity-changes` 审批页共同构成两阶段流程；导航没有新增顶级项，审批入口在 `/development` 页头。

- 发起只调 `POST /v4/identity-changes`，请求体只有 `userId`、`toIdentity`、`reason`（≤500）。**`fromIdentity` 不在请求内**：服务端取目标用户当前 `identity_id` 快照，首次登记为 `null`，前端自带等于伪造快照。
- 目标身份必须来自 `GET /v2/content/identities/page`（分页拉全、按 `level` 升序、最多 20 × 100 条并带截断降级）。字典加载失败时禁用提交并提供重试，**不使用本地兜底列表、不硬编码「积极分子/发展对象」等名称**。
- 「目标身份与当前身份相同，无需变更」「该用户已有待审批的身份变更单」都是服务端校验：界面允许提交并原样展示 400 原文，不预先禁用选项或按钮。二次确认框展示「当前身份 → 目标身份」，`identityId` 为空显示「未登记」。
- 提交成功**不刷新档案**（变更单尚未生效，此时身份不会变），也不本地改写 `identityName`；页面提示「审批通过后请点页头『重新读取』回读档案身份」，页头确实提供「重新读取」按钮触发一次真实档案请求，生效只能由重新请求的服务端数据体现。
- 审批 `POST /v4/identity-changes/{id}/review` **仅超管**（`hasRole('SUPER_ADMIN')`），请求体只有 `{ pass, remark }`（remark ≤50）。支委能进审批页但**不渲染通过/驳回按钮**，而不是渲染后必然被拒。
- `managed/page` 的能力差异必须显式化：超管走 `pageForAdmin`，`status` 与 `userId` 两个过滤都生效，因此界面提供三态筛选与按成员编号精确过滤（后端**不支持按姓名模糊搜索**，界面写明）；支委走 `pageForBranch`，**这两个参数被服务端直接丢弃**，因此支委视图不发送它们、也不渲染对应控件，并注明「固定展示本支部全部变更单，不支持筛选」。
- 越权读单与真不存在同为「变更单不存在」，页面原样转达，不改写成「无权限」，也不据此推断单据是否存在。
- 已处理单（`status` 非 1）的审批按钮禁用；服务端「该变更单已处理，不能重复审批」原文可展示。审批意见超 50 字时给出字段级错误并聚焦到该输入框，不是只在顶部报警。`status` 只有 1 待审批 / 2 已生效 / 3 驳回三种，未知值显示「未知状态（x）」且标签不用成功色，**不与思想汇报的 1/2/3 共用映射**。
- **身份变更不联动登录角色**（红线）：审批通过只写 `tb_user_detail.identity_id`，`role_id`、菜单与权限矩阵一概不变。前端不得因身份变成「正式党员」而修改 `currentRole`、导航或路由权限；回归中断言生效后 store 的 `currentRole` 与导航项不变。
- 页面同样用请求序号 + `captureSessionIdentity()` 隔离快速切换筛选、换号、退出与卸载后的迟到响应；写操作同步置位，同一事件循环内双击只发一次请求。

`/development/batch` 已从前端路由移除：后端没有批量身份调整端点，保留一个通往空占位页的活跃入口比移除更误导；`src/views/development/BatchAdjust.vue` 保留为设计参考并在文件头注明不得挂回路由。
