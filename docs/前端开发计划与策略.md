# 党建云平台前端开发计划与策略

> 来源：《党建云平台项目框架.docx》

> 整理范围：仅提取和归纳与 Web 前端、微信小程序及前后端协作有关的开发内容。本文不是原文逐字转录；“待确认事项”是根据原文内部差异整理出的实施风险。

## 1. 前端建设目标

党建云平台的前端应围绕“党员发展全过程管理”展开，服务超级管理员、支部管理员和普通成员三类用户，覆盖成员培养、活动组织、数据统计和公共信息展示等场景。

前端建设目标包括：

- 为不同角色提供与权限匹配的工作界面和数据范围。
- 将成员身份变化、培养材料、思想汇报、党校学习和活动记录汇总为可查询的电子培养档案。
- 支持活动创建、发布、报名、签到、统计和归档的完整操作链路。
- 支持成员 Excel 导入、批量操作、数据导出和错误报告下载。
- 通过首页统计卡片、待办事项和快捷入口提升管理效率。
- 通过微信小程序承载移动端报名、扫码签到和个人培养信息查询。
- 通过“党建智能助手”提供功能导航、页面指引和常见问题回答。

## 2. 前端范围与终端划分

### 2.1 Vue 3 Web 管理端

Web 管理端是主要业务终端，面向老师、支委和普通成员，承担：

- 登录认证后的用户信息与权限加载；
- 首页数据看板和个人培养概览；
- 成员、党支部和党员发展过程管理；
- 活动创建、管理、签到监控和数据统计；
- 新闻、公告、下载资源和个人资料管理；
- 电子培养档案查看与导出；
- 智能导航助手。

### 2.2 微信小程序

微信小程序主要承担移动场景：

- 活动报名；
- 动态二维码扫码签到；
- 个人培养信息查询；
- 请假申请可作为二期功能。

### 2.3 前后端协作边界

- 前端负责页面展示、交互、表单校验、权限入口控制和接口状态反馈。
- 后端负责业务权限、数据范围、身份变更规则、签到校验和操作日志等最终校验。
- 前端隐藏无权限入口不能替代后端鉴权。
- 文件由 MinIO 等文件服务保存，前端负责上传、下载、进度和错误提示。

## 3. 总体前端策略

### 3.1 角色与党员身份分离

系统角色决定用户可以使用哪些功能，党员身份表示成员当前所处的发展阶段。前端状态模型、路由权限和组件判断必须分别保存这两类信息，避免混用。

系统角色：

| 角色 | 数据范围 | 主要能力 |
| --- | --- | --- |
| 超级管理员 | 全院 | 成员导入、支部管理、身份审批或调整、全部档案、全部活动和统计 |
| 支部管理员（支委） | 所属党支部 | 本支部成员、培养记录、活动和统计管理 |
| 普通成员 | 个人及可参与内容 | 个人资料、个人培养档案、活动参与、思想汇报 |

党员发展身份按统一字典维护，不允许页面自行定义。原文涉及普通学生、入党申请人、积极分子、发展对象、预备党员、正式党员等阶段，并建议将身份从自由字符串改为枚举或字典值。

### 3.2 动态权限与数据范围

- 登录后获取当前用户、系统角色、所属支部和党员身份。
- 菜单、首页卡片、页面按钮和可选操作根据角色动态展示。
- 超级管理员可查看全院数据；支委只可查看和操作本支部数据；普通成员只可操作个人数据。
- 批量操作、身份调整、党支部调整等高风险操作必须二次确认。
- 身份历史和签到记录在前端不提供删除入口。
- 对接口返回的 `401`、`403` 和数据越权错误提供统一反馈。

### 3.3 模块化与复用

前端应按业务域拆分页面和接口模块，并复用以下通用能力：

- 列表查询：分页、筛选、重置、导出和空状态；
- 表单：新增、编辑、详情查看和字段权限；
- 文件：上传、预览、下载、格式与大小校验；
- 批量操作：勾选、确认、进度、成功与失败结果；
- 字典：角色、党员身份、活动类型和活动状态；
- 权限：路由、菜单、按钮和数据范围；
- 状态反馈：加载、成功、失败、无权限和网络重试。

### 3.4 数据驱动的可扩展设计

- 活动类型、党员身份等采用后端字典或枚举，不在多个页面重复硬编码。
- 首页卡片、快捷入口和待办事项由角色及接口数据驱动。
- 智能助手一期采用固定问答和关键词匹配，预留 `/api/ai/chat`，后期再接入大模型。
- 活动参与范围支持按身份、支部或指定成员配置，前端使用统一的选择组件表达。

## 4. 信息架构与页面计划

### 4.1 登录与应用框架

计划页面与能力：

- 登录入口；
- 统一认证回调与登录状态恢复；
- 当前用户信息加载；
- 退出登录；
- 动态菜单和无权限页面；
- 全局消息、文件上传和异常提示。

文档明确提出使用学校统一身份认证平台，平台不保存密码，也不提供自主注册和密码修改。学号或工号、姓名、学校身份来自认证系统且不可修改。

### 4.2 首页

首页按角色展示不同内容：

- 超级管理员：首页统计全院成员、发展阶段、活动、思想汇报和身份调整待办。
- 支部管理员：仅展示所属党支部的数据和待办。
- 普通成员：突出个人培养进度、活动、材料和通知。

统计卡片应支持点击后进入对应业务列表，并带入适当筛选条件。

### 4.3 成员管理

成员管理是基础数据模块，优先级最高。

主要页面：

- 成员列表：分页、学院、年级、专业、班级、党支部和党员身份筛选；
- 成员详情：基本信息、联系方式、所属支部和当前党员身份；
- Excel 导入：模板下载、文件上传、校验结果、导入结果和错误报告；
- 批量操作：导出、调整党支部、设置培养联系人、停用和恢复。

字段编辑策略：

| 字段 | 前端处理 |
| --- | --- |
| 手机号、邮箱、头像 | 在权限允许时提供编辑入口 |
| 学号、姓名、学院、班级 | 展示为只读 |
| 党员身份 | 只能通过身份调整流程修改 |

Excel 导入前端需校验 `.xlsx` 格式，展示后端返回的逐行错误，并提供错误报告下载。学号、姓名等业务规则仍以服务端校验结果为准。

### 4.4 党员发展与培养档案

主要页面：

- 成员培养主页：左侧基础信息，右侧集中展示培养信息；
- 当前身份与身份调整；
- 批量身份调整；
- 身份历史详情；
- 培养联系人维护；
- 培养材料上传和管理；
- 思想汇报和党校学习记录；
- 电子培养档案查看与 PDF 导出；
- 按学院、专业、班级和党支部的培养统计。

交互策略：

- 页面顶部持续显示当前发展阶段。
- 身份调整使用独立对话框或表单，展示目标身份、调整时间和备注等信息。
- 提交前二次确认，成功后刷新当前身份和历史记录。
- 身份历史只读，禁止删除。
- 培养材料支持 PDF、Word、图片和 ZIP。

### 4.5 活动管理

活动模块覆盖完整生命周期：

```mermaid
flowchart LR
  A[创建草稿] --> B[编辑活动]
  B --> C[发布]
  C --> D[报名或确定参与范围]
  D --> E[二维码签到]
  E --> F[统计参与情况]
  F --> G[活动归档]
  G --> H[同步个人培养档案]
```

主要页面：

- 活动列表：名称、类型、支部和时间筛选；
- 新建或编辑活动；
- 活动详情；
- 签到二维码与实时签到名单；
- 请假、迟到、缺席管理；
- 活动统计和签到数据导出；
- 活动归档与复制。

活动表单至少包含活动名称、类型、举办支部、负责人、地点、简介、封面、活动时间、签到时间和参与范围。

签到二维码默认每 60 秒刷新一次，前端显示有效期倒计时并自动请求新二维码。签到监控页应实时更新人数和名单。活动未开始、已截止、非参与对象、重复签到、二维码过期和网络异常均需给出明确提示。

### 4.6 新闻、公告与下载专区

- 新闻列表与详情；
- 公告列表、详情和置顶展示；
- 党建成果和相关网站入口；
- 下载资源分类、列表和下载；
- 管理员上传资源及查看下载次数。

资源分类包括申请书模板、思想汇报、学习资料、常用表格和其他。

### 4.7 数据统计

统计页面包括：

- 全院及各支部成员数量；
- 各培养阶段人数；
- 活动参与率和签到状态；
- 二课学时；
- 思想汇报完成情况；
- 党校学习完成率。

图表需支持按学院、专业、班级、支部和时间范围筛选，并为老师与支委应用不同的数据范围。

### 4.8 个人中心

普通成员可查看姓名、学号、学院、专业、班级、所属支部和党员身份，只能修改手机号、邮箱、头像和个人简介等个人字段。

个人中心还应汇总：

- 个人培养档案；
- 身份历史；
- 思想汇报和培养材料；
- 活动参与及签到记录；
- 党校学习记录。

### 4.9 党建智能助手

一期定位为“智能导航助手”，优先解决用户找不到功能的问题。

界面策略：

- 使用右下角悬浮按钮打开聊天面板；
- 顶部提供“创建活动”“导入名单”“调整身份”“下载模板”“查看培养档案”“党校学习”等快捷问题；
- 使用关键词匹配返回功能路径和常见问题答案；
- 回答中的功能入口可直接跳转到对应页面；
- 后期通过统一接口替换为大模型服务。

## 5. 接口对接计划

文档给出的接口域可整理为：

| 领域 | 前端主要用途 | 接口草案 |
| --- | --- | --- |
| 认证 | 登录跳转、回调、当前用户、退出 | `/api/auth/*` |
| 用户 | 个人资料、头像 | `/api/user/*` |
| 成员 | 列表、详情、增改、导入导出、身份调整 | `/api/member/*` |
| 活动 | 列表、详情、创建、编辑、发布、二维码、统计 | `/api/activity/*` |
| 签到 | 签到、个人记录、活动签到名单 | `/api/sign/*` |
| 内容 | 新闻、公告、成果、党建网站 | `/api/news/*`、`/api/notice/*` 等 |
| 资源 | 资源列表与文件下载 | `/api/resource/*` |
| 统计 | 首页、活动和成员统计 | `/api/statistics/*` |
| 助手 | 问答或功能导航 | `/api/ai/chat` |

对接策略：

1. 为每个业务域建立独立的 TypeScript 类型和 API 模块。
2. 统一处理基础地址、Token、超时、业务错误码和登录失效。
3. 列表接口统一使用分页参数和 `{ total, rows }` 类响应结构。
4. 文件上传使用 `multipart/form-data`，文件下载正确处理二进制响应和文件名。
5. 在接口未完成时使用与目标响应结构一致的 Mock 数据，页面中保留清晰的替换点。
6. 联调前由前后端共同确认接口路径、HTTP 方法、字段名、枚举值、分页结构和错误码。

## 6. 分阶段开发计划

原文的总体顺序是先完成数据库和后端基础设施，再依次开发成员、活动、签到、首页和智能助手。转换为前端可执行计划如下。

### 阶段 0：基础能力与契约确认

- 确认登录方案、角色编码、党员身份字典和数据范围规则。
- 确认接口契约、统一响应结构、分页格式和错误码。
- 建立请求层、登录状态、路由权限、动态菜单和公共布局。
- 建立通用列表、筛选、表单、上传下载和批量确认模式。

交付结果：用户可以完成认证，进入与角色匹配的应用框架；前后端具备稳定的联调基线。

### 阶段 1：成员管理

- 成员列表、筛选、分页和详情；
- 成员信息编辑权限；
- Excel 模板、导入、结果预览和错误报告；
- 导出、党支部调整和其他批量操作；
- 操作结果与日志查询入口。

交付结果：管理员和支委可以在各自数据范围内完成成员基础信息管理。

### 阶段 2：党员发展管理

- 培养主页；
- 单人和批量身份调整；
- 身份历史；
- 培养联系人；
- 培养材料、思想汇报和党校学习；
- 电子培养档案及导出。

交付结果：成员发展过程可完整查看、维护和追溯。

### 阶段 3：活动管理

- 活动列表、详情、新建和编辑；
- 发布、参与范围和状态展示；
- 请假、统计、导出、归档和复制；
- 活动记录同步至个人档案。

交付结果：Web 端可以完成活动全生命周期管理。

### 阶段 4：二维码签到与小程序

- Web 端生成和刷新签到二维码；
- 实时签到监控；
- 小程序扫码、校验结果和个人签到记录；
- 过期、重复、越权和网络异常处理。

交付结果：活动现场签到可在 Web 管理端与微信小程序之间闭环运行。

### 阶段 5：首页、内容与统计

- 分角色首页；
- 新闻、公告、党建成果和相关网站；
- 下载专区；
- 成员、活动和培养统计图表；
- 卡片和图表到业务页面的联动跳转。

交付结果：平台具备完整门户、内容服务和管理看板。

### 阶段 6：智能导航助手

- 快捷问题；
- 固定问答和关键词匹配；
- 可点击的页面导航；
- 预留智能问答接口。

交付结果：用户可以通过自然语言或快捷问题定位平台功能。

## 7. 质量与验收策略

### 7.1 权限验收

- 三类角色看到正确的菜单、按钮和数据范围。
- 支委不能查看或操作其他支部数据。
- 普通成员不能修改学号、姓名、学院和党员身份。
- 越权接口返回后，前端能正确提示并保持页面状态安全。

### 7.2 业务流程验收

- Excel 导入能展示成功、失败和错误明细。
- 身份调整后，当前身份与历史记录同步更新。
- 活动从创建到归档状态流转正确。
- 二维码按配置刷新，重复、过期和非参与对象签到均有准确反馈。
- 活动结果能够同步到成员个人培养档案。

### 7.3 体验与稳定性验收

- 所有异步页面具备加载、空数据、错误和重试状态。
- 批量及不可逆业务操作具备二次确认。
- 上传文件在前端进行格式和大小预检，并展示进度。
- 表单错误定位到具体字段，业务错误保留用户已填写内容。
- 常用管理页面兼顾常见桌面分辨率，普通成员页面兼顾移动端浏览。

## 8. 待确认事项

以下内容在原文中存在缺失或前后不一致，需要在实施前形成明确结论：

1. **登录方式**：正文要求学校 SSO，但部分接口说明仍出现登录端点，需确认正式环境、开发环境和演示环境各自的认证流程。
2. **角色编码**：正文使用“超级管理员、支部管理员、普通成员”，接口示例使用 `teacher`、`branch_admin`、`student`，需统一前后端枚举。
3. **党员身份全集**：原文多处列出的阶段不完全一致，需确定完整顺序、允许的流转关系和后端字典值。
4. **身份调整审批**：部分章节写支委直接调整，部分权限描述写支委提交申请，需确认是否存在审批流程。
5. **导航形态**：原文提出动态左侧菜单，现有产品方案可能采用顶部导航，需确定最终信息架构及移动端行为。
6. **活动报名**：原文标注为可选能力，需确认一期是否实现，以及不报名活动如何生成参与名单。
7. **实时签到更新方式**：需确认轮询、Server-Sent Events 或 WebSocket 方案。
8. **接口规范**：接口草案中路径、方法、分页结构和字段仍是概念设计，需在联调前形成正式 API 契约。
9. **操作日志界面**：原文要求记录日志，但未明确普通管理员是否具有查看页面及具体筛选权限。
10. **一期范围**：思想汇报、党校学习、请假申请和智能助手的优先级需与项目排期再次对齐。

## 9. 建议的阶段性产物

每个阶段应同步维护以下成果：
